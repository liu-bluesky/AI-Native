# 万物皆插件架构设计

## 1. 文档目的

本文档描述桌面本地智能体系统的插件化整改方向。当前系统中的内置工具、MCP、Skill、Rule、Agent、Connector 和 Workflow 存在不同的配置与执行方式；本方案将这些能力统一抽象为插件，并通过统一的注册、发现、选择、授权和执行流程提供给 AI。

本文档只描述产品和系统设计，不包含具体代码实现。实际开发应以本文档确认后的插件协议、数据模型和迁移边界为准。

## 2. 核心理念

系统采用“万物皆插件”的设计原则：

```text
所有可被系统发现、配置、组合或执行的能力，统一视为插件。
```

插件可以提供一种或多种能力，例如：

- 工具能力：读取文件、执行命令、搜索网络。
- 技能能力：前端开发、代码审查、部署流程。
- 规则能力：工作区安全规则、项目开发规范。
- 智能体能力：前端 Agent、部署 Agent、代码审查 Agent。
- 外部服务能力：MCP Server、飞书连接器、模型供应商。
- 流程能力：构建流程、测试流程、部署流程。
- 界面能力：设置面板、对话操作、状态面板和工作区窗口。

插件化的重点不是把所有内容放进同一种文件，而是让所有能力遵守统一的生命周期和元数据协议。

## 3. 总体架构

```text
万物皆插件
  │
  ├── Plugin Registry
  │   ├── Builtin Tool Plugin
  │   ├── MCP Plugin
  │   ├── Skill Plugin
  │   ├── Agent Plugin
  │   ├── Connector Plugin
  │   └── Workflow Plugin
  │
  ├── Capability Registry
  │   ├── Tool Registry
  │   ├── Skill Registry
  │   ├── Rule Registry
  │   ├── Agent Registry
  │   └── Provider Registry
  │
  └── AI Context Pipeline
      ├── 发布插件摘要
      ├── AI 选择 Skill
      ├── 加载 Skill 正文
      ├── 选择 Tool
      ├── 参数校验
      ├── 权限检查
      ├── 执行 Tool
      └── 把结果回传模型
```

## 4. Plugin Registry

Plugin Registry 是插件登记中心，负责管理插件的来源、状态、版本和生命周期。

### 4.1 插件类型

第一阶段支持以下插件类型：

| 类型 | 作用 |
| --- | --- |
| `tool` | 提供可以被 Runtime 执行的工具 |
| `mcp` | 接入一个或多个 MCP Server |
| `skill` | 提供 AI 的任务指导和使用规范 |
| `rule` | 提供必须遵守的约束 |
| `agent` | 组合工具、技能、规则和模型形成专用智能体 |
| `connector` | 接入飞书、GitHub 等外部服务 |
| `workflow` | 描述可复用的多步骤执行流程 |
| `provider` | 提供模型或媒体能力 |
| `ui` | 提供插件设置、按钮或界面入口 |

### 4.2 插件基础信息

每个插件至少需要具备以下信息：

- 唯一插件 ID。
- 插件类型。
- 显示名称和描述。
- 版本号。
- 插件来源。
- 当前状态。
- 提供的能力列表。
- 依赖的其他插件。
- 所需配置。
- 权限和风险等级。
- AI 使用说明。
- UI 展示信息。

### 4.3 插件来源

插件来源统一标记，便于覆盖、诊断和审计：

- `builtin`：应用内置插件。
- `system`：系统级插件。
- `project`：项目级插件。
- `user`：用户级插件。
- `mcp`：MCP 动态发现的插件。
- `marketplace`：插件市场安装的插件。
- `runtime`：Runtime 临时注册的插件。

### 4.4 插件状态

- `enabled`：已启用，可以被发现和使用。
- `disabled`：已禁用，不参与 AI 选择。
- `unavailable`：插件存在，但依赖或配置不满足。
- `loading`：正在加载。
- `failed`：加载失败，需要诊断。
- `deprecated`：已废弃，不建议新任务使用。

## 5. Capability Registry

Capability Registry 负责登记插件提供的具体能力。插件是能力的承载单元，Registry 是能力的查询入口。

### 5.1 Tool Registry

登记真正可执行的工具，包括：

- 工具名称。
- 所属插件。
- 输入参数协议。
- 输出结果协议。
- 风险等级。
- 是否需要用户授权。
- 作用范围。
- 执行器。
- 可用条件。
- 替代工具。

### 5.2 Skill Registry

登记供 AI 选择的技能，包括：

- 技能名称。
- 技能描述。
- 适用场景。
- 不适用场景。
- 依赖工具。
- 推荐组合。
- 互斥技能。
- 是否允许模型自动调用。
- 是否允许用户显式调用。
- 技能正文位置。

### 5.3 Rule Registry

登记必须遵守的规则，例如：

- 文件访问范围规则。
- 命令执行安全规则。
- 项目编码规范。
- 数据隐私规则。
- 部署确认规则。

规则可以按作用域生效：

- 系统级。
- 用户级。
- 项目级。
- 会话级。
- Agent 级。

### 5.4 Agent Registry

登记可以被选择或启动的智能体。Agent 不直接复制工具实现，而是引用已有插件：

```text
前端开发 Agent
  ├── 前端开发 Skill
  ├── 前端代码 Rule
  ├── 文件读取 Tool
  ├── 文件修改 Tool
  ├── 命令执行 Tool
  └── 前端模型 Provider
```

### 5.5 Provider Registry

登记模型和外部服务供应商，包括：

- 文本模型。
- 推理模型。
- 图片生成模型。
- 视频生成模型。
- 音频生成模型。
- 音频转写模型。
- 网络搜索服务。

## 6. AI Context Pipeline

AI Context Pipeline 负责把插件能力转换成 AI 可以理解和使用的上下文。

### 6.1 发布插件摘要

Runtime 不应该把所有插件的完整内容一次性放入模型上下文，而是先发布摘要目录：

- 插件名称。
- 能力类型。
- 简短描述。
- 适用场景。
- 风险等级。
- 依赖和限制。

摘要用于路由，不代表完整执行规则。

### 6.2 AI 选择 Skill

AI 根据用户需求选择一个或多个 Skill：

```text
用户需求
  ↓
识别任务意图
  ↓
匹配 Skill 描述
  ↓
检查 Skill 前置条件
  ↓
检查依赖、冲突和作用域
  ↓
选择适用 Skill
```

简单问答可以不加载 Skill；复杂任务应先选择对应的工作流或领域 Skill。

### 6.3 加载 Skill 正文

AI 选中 Skill 后，Runtime 再加载 Skill 的完整正文。Skill 正文负责告诉 AI：

- 任务应该如何拆分。
- 应该先读取什么信息。
- 应该使用哪些工具。
- 工具调用顺序是什么。
- 哪些行为禁止执行。
- 如何处理失败和中断。
- 如何验证最终结果。

### 6.4 选择 Tool

Skill 不执行动作，只指导 AI 选择 Tool。

例如：

```text
前端修改 Skill
  ├── 先使用 list_files 了解结构
  ├── 使用 search_text 定位代码
  ├── 使用 read_file 读取上下文
  ├── 使用 apply_patch 修改文件
  └── 使用 run_command 执行构建和测试
```

### 6.5 参数校验

Runtime 根据 Tool Registry 中的输入协议校验工具参数：

- 参数是否完整。
- 参数类型是否正确。
- 路径是否在允许范围内。
- 工具是否适用于当前会话。
- 当前插件是否可用。

### 6.6 权限检查

权限检查在实际执行前进行，不能只依赖 Skill 文本约束。

需要检查：

- 是否需要用户确认。
- 当前用户是否拥有权限。
- 是否超出工作区范围。
- 是否涉及敏感数据。
- 是否属于命令、删除、部署或网络写操作。
- 当前 Agent 是否允许使用该工具。

### 6.7 执行和回传

Tool Executor 负责实际执行，Runtime 负责记录过程并把结果回传模型。

```text
Tool Call
  ↓
Schema 校验
  ↓
Permission Gate
  ↓
Tool Executor
  ↓
审计和事件记录
  ↓
Tool Result
  ↓
返回模型继续决策
```

模型可以根据结果继续调用工具、向用户提问、暂停任务或结束任务。

## 7. Skill 设计原则

### 7.1 Skill 不是 Tool

- Skill 负责说明如何完成任务。
- Tool 负责执行具体动作。
- Skill 不能绕过权限。
- Tool 不能依赖模型自行遵守隐含规则。

### 7.2 Skill 摘要和正文分离

摘要用于发现和路由；正文用于执行指导。这样可以降低上下文长度，也避免无关技能干扰模型。

### 7.3 Skill 支持调用策略

每个 Skill 需要明确：

- 是否允许模型自动选择。
- 是否允许用户显式调用。
- 是否只在特定 Agent 中可用。
- 是否只在特定项目或工作区可用。

### 7.4 Skill 支持组合关系

Skill 之间需要支持以下关系：

- `requires`：必须依赖。
- `recommends`：推荐一起使用。
- `conflicts`：不能同时使用。
- `fallbacks`：失败时的备用技能。
- `composes_with`：可以组合使用。

## 8. 内置工具插件设计

当前内置工具应作为一个或多个 Builtin Tool Plugin 管理，而不是只作为 Runtime 中的散落函数。

建议按能力域划分：

```text
Builtin Tool Plugins
├── filesystem
│   ├── list_files
│   ├── read_file
│   ├── search_text
│   ├── apply_patch
│   ├── write_file
│   └── delete_file
├── command
│   ├── check_command_risk
│   ├── run_command
│   └── process
├── network
│   ├── http_get
│   ├── http_post
│   ├── web_search
│   ├── web_extract
│   └── download_file
├── media
│   ├── generate_image
│   ├── edit_image
│   ├── generate_video
│   ├── generate_audio
│   └── transcribe_audio
├── project
│   ├── list_projects
│   ├── get_project
│   └── deployment tools
└── interaction
    ├── ask_user_question
    └── update_execution_plan
```

每个工具同时拥有三类信息：

1. Runtime 工具契约：参数、结果、执行器。
2. AI 选择说明：什么时候使用、什么时候不要使用。
3. 安全策略：风险、授权、范围和失败处理。

### 8.1 图片工具插件试点

第一批试点插件使用目录化插件包，位于：

```text
web-admin/frontend/src-tauri/src/liuagent_core/plugin_system/plugins/
└── builtin-media-image/
    ├── plugin.json
    ├── tools/
    ├── runtime.rs
    ├── skills/
    │   ├── image-generation/SKILL.md
    │   └── image-editing/SKILL.md
    ├── rules/
    └── schemas/
```

插件 ID 为 `builtin-media-image`，当前注册四项能力：

```text
builtin.media.image.generate          Tool
builtin.media.image.edit              Tool
builtin.media.image.generation-skill  Skill
builtin.media.image.editing-skill     Skill
```

该插件负责描述能力、选择规则、输入输出 Schema、权限以及图片执行逻辑。Skill 正文使用项目现有的标准 `SKILL.md` 格式，独立于 Rust 代码。图片生成和编辑的 Provider 请求、参数构造和结果解析位于插件内部 `runtime.rs`；`tools/media.rs` 只保留视频、音频等其他媒体的后端调用。

```text
builtin-media-image.runtime.execute_builtin_media_image_tool
```

Rust 代码只负责读取并注册 `plugin.json`，统一入口为 `builtin_plugins_registry()`。后续新增文件、命令、网络或 MCP 插件时，由该入口聚合注册；Runtime 只依赖 Registry，不直接依赖每个插件的具体模块。

当前试点验证范围：

- 插件 Manifest 可以通过基础校验。
- 图片生成和图片编辑能力可以被统一注册。
- 旧 `definitions.rs` 不再重复声明图片工具，ToolDefinition 改由图片插件适配层提供。
- Skill 能表达适用场景、规避场景、推荐能力和冲突能力。
- Resolver 可以按能力类型和优先级返回候选能力。
- 图片生成和编辑执行器已经移动到插件内部。

### 8.3 媒体插件统一附件规范

媒体类插件必须使用统一的附件模型。任何入口产生的图片都必须先转换成统一附件，再交给媒体插件；不能让不同入口分别维护自己的图片引用格式。

统一附件最少包含：

```json
{
  "attachmentId": "asset-或-context-ref-唯一标识",
  "kind": "image",
  "mimeType": "image/png",
  "fileName": "可选原始文件名",
  "dataUrl": "data:image/...;base64,...",
  "source": "upload|extension|history_context|generated",
  "sourceMessageId": "可选历史消息 ID",
  "sourceUrl": "可选原始地址"
}
```

统一处理链路：

```text
拖拽 / 文件选择 / 扩展添加 / 鼠标右键追加历史图片
  ↓
读取或物化原始图片
  ↓
校验 kind、mimeType、attachmentId 和 dataUrl
  ↓
写入统一附件上下文
  ↓
传给 Harness / Provider
  ↓
edit_image 使用 input_asset_ids 查找同一份附件
```

以下链路禁止直接交给图片编辑插件：

- 只有图片组件的 `src` 或 `currentSrc`，没有原始内容。
- 只有 `blob:`、`asset:` 或临时预览地址，没有可持久化读取能力。
- 只有历史消息展示 URL，没有对应的统一 `attachmentId`。
- 只有上下文引用 ID，但没有能解析为真实图片内容的附件记录。

#### 8.3.1 入口差异和历史问题

当前容易出现问题的两条链路如下：

| 入口 | 当前数据形态 | 风险 |
| --- | --- | --- |
| 拖拽、文件选择、扩展添加 | 真实 `File` → `uploadFiles` → `attachmentId` → `data:image/...;base64,...` | 通常可以被 `edit_image` 读取 |
| 鼠标右键追加历史图片 | 展示 URL → `composerContextRefs` → `context-ref-*` | 可能丢失原始文件、MIME、Data URL 或持久化资产信息 |

两者表面上都是图片，实际却不是同一种数据：

```text
拖拽 / 扩展：真实文件附件
右键追加：历史媒体引用
```

因此，右键追加历史图片时不能只保存 `src` 或 `currentSrc`。必须先把历史图片物化为可读取的 `dataUrl` 或持久化本地附件，并生成与上传附件相同语义的 `attachmentId`、`kind`、`mimeType` 和内容字段。

如果历史图片无法读取，发送前必须明确提示“原图不可读取，无法编辑”，不能让 AI 先调用 `edit_image` 后才在插件内部失败。

#### 8.3.2 媒体插件验收条件

每一个新的媒体插件至少需要通过以下测试：

- 拖拽图片可以被插件读取和编辑。
- 文件选择图片可以被插件读取和编辑。
- 扩展添加图片可以被插件读取和编辑。
- 鼠标右键追加历史图片可以被插件读取和编辑。
- 历史图片 URL 失效时，发送前能返回明确错误。
- `input_asset_ids` 能唯一映射到统一附件记录。
- `dataUrl`、MIME 类型和图片内容不会在跨层传递时丢失。
- macOS 和 Windows 的本地附件路径、资源协议和临时文件处理结果一致。

## 9. MCP 插件设计

MCP Server 作为 MCP Plugin 接入，不单独维护一套 AI 选择逻辑。

MCP 插件的流程是：

```text
加载 MCP Plugin
  ↓
读取 Server 配置
  ↓
建立 stdio / HTTP / SSE 连接
  ↓
调用 tools/list
  ↓
发现 MCP 工具
  ↓
写入 Tool Registry
  ↓
参与和内置工具相同的 AI 选择流程
```

MCP 工具需要和内置工具一样声明：

- 工具名称。
- MCP Server 来源。
- 输入 Schema。
- 输出结果。
- 是否需要授权。
- 访问范围。
- 超时和失败策略。

MCP Host 管理接口属于 Runtime 内部能力，不应直接暴露给普通模型作为业务工具。

## 10. 插件生命周期

插件需要有统一生命周期：

```text
发现
  ↓
加载
  ↓
校验
  ↓
注册能力
  ↓
启用
  ↓
运行
  ↓
禁用 / 更新
  ↓
卸载
  ↓
释放资源
```

插件退出时必须清理：

- 事件监听器。
- 后台进程。
- MCP 连接。
- 文件监控器。
- 定时器。
- 临时缓存。
- UI 状态订阅。

## 11. 权限和审计

权限由 Runtime 强制执行，Skill 和插件说明不能替代安全检查。

工具风险建议分为：

- `low`：读取、查询、计划和状态查看。
- `medium`：写文件、执行命令、访问网络。
- `high`：删除、部署、外部系统写入和敏感数据操作。

每次插件调用需要记录：

- 插件 ID。
- 能力 ID。
- Skill ID。
- Tool Call ID。
- 输入参数摘要。
- 工作区和会话。
- 权限决定。
- 执行结果。
- 错误信息。
- 开始和结束时间。

## 12. 当前系统整改范围

整改不改变现有工具的实际能力，先统一它们的管理和调用方式。

### 第一阶段

- 建立 Plugin Registry 概念。
- 建立 Tool Registry 和 Skill Registry。
- 将内置工具按能力域归类。
- 为内置工具提供统一的 AI 选择说明。
- 统一工具风险、权限和输入输出描述。
- 保留现有 Runtime 执行器作为底层执行实现。

### 第二阶段

- 将 MCP Server 和 MCP Tool 接入统一 Registry。
- 将现有 Skill、Rule 和 Agent 纳入统一发现流程。
- 增加插件来源、版本和优先级管理。
- 增加插件启用、禁用和诊断能力。

### 第三阶段

- 将 Connector、Workflow、Provider 和 UI 纳入插件体系。
- 支持插件依赖和组合。
- 支持插件包安装、导入、导出和升级。
- 支持插件市场或组织级插件分发。

## 13. 非目标

本方案当前不包含以下内容：

- 不立即重写现有工具执行代码。
- 不把权限控制交给 Markdown 或模型自行判断。
- 不把所有插件正文一次性塞进模型上下文。
- 不让 MCP Host 内部管理接口直接暴露给普通模型。
- 不要求 macOS 和 Windows 使用不同的插件协议。
- 不因为插件化而复制现有工具实现。

## 14. 设计结果

整改完成后，系统统一遵循以下关系：

```text
插件 = 能力的注册、配置和生命周期

Skill = AI 如何选择和使用能力的说明

Tool = 能力的实际执行接口

Rule = 必须遵守的约束

Agent = 插件、Skill、Tool、Rule 和 Provider 的组合

Runtime = 统一负责发现、调度、授权、执行、审计和恢复
```

最终 AI 的工作方式变为：

```text
理解用户需求
  ↓
发现可用插件摘要
  ↓
选择合适 Skill
  ↓
加载 Skill 正文
  ↓
选择具体 Tool
  ↓
执行参数和权限校验
  ↓
调用内置工具或 MCP 工具
  ↓
读取执行结果
  ↓
继续任务或返回最终结果
```
