# 桌面智能体动态任务上下文与提示词按需注入设计

## 1. 当前结论

自 2026 年 8 月 3 日起，桌面智能体不再在每轮主模型请求前执行独立的 AI Task Router。

当前主链路为：

```text
用户消息
  ↓
Runtime 确定性生成 TaskProfile
  ↓
按 TaskProfile 注入必要的动态上下文
  ↓
主模型直接理解任务并决定回答或调用工具
  ↓
Runtime 在工具边界执行权限、风险和验证约束
```

设计原则：

- 不为通用意图分类额外调用一次模型。
- 不要求模型先输出严格的任务分类 JSON。
- 权限、风险、能力范围和交付要求由 Runtime 负责。
- 主模型直接结合用户消息、系统提示词和可用工具理解任务。
- 动态上下文继续按需注入，不恢复全量大提示词。

## 2. 移除前置模型路由的原因

独立前置模型分类会增加以下成本和故障点：

- 每轮对话增加一次模型请求和等待时间。
- checkpoint 恢复时会重复执行与主任务无关的分类请求。
- 流式内容、严格 JSON、Schema 和 provider 兼容性都会成为主循环启动前的阻塞点。
- 分类模型与主模型可能对同一请求产生不同理解。
- Runtime 最终仍需重新计算权限、风险、能力和交付约束，职责重复。

因此，语义理解交给主模型，确定性约束留在 Runtime。

## 3. TaskProfile 的职责

`TaskProfile` 保留，但它不再来自独立模型输出。

Runtime 通过 `build_task_profile(user_message)` 生成：

```rust
pub struct TaskProfile {
    pub version: String,
    pub intent: TaskIntent,
    pub domains: Vec<String>,
    pub goal: String,
    pub targets: Vec<String>,
    pub clarity_score: u8,
    pub ambiguities: Vec<String>,
    pub complexity: String,
    pub risk: String,
    pub required_context: Vec<String>,
    pub required_capabilities: Vec<String>,
    pub source: String,
}
```

其中：

| 字段 | 责任方 | 用途 |
|---|---|---|
| `intent` | Runtime | 区分回答、设计、诊断和明确执行 |
| `domains` | Runtime | 决定代码、UI、安全、媒体、部署等上下文 |
| `goal` | Runtime | 生成简短任务目标 |
| `targets` | Runtime | 提取用户明确给出的路径和对象 |
| `clarity_score` | Runtime | 提供基础清晰度状态 |
| `complexity` | Runtime | 控制计划和上下文策略 |
| `risk` | Runtime | 描述只读、普通写入或更高风险操作 |
| `required_context` | Runtime | 选择需要注入的上下文来源 |
| `required_capabilities` | Runtime | 描述完成任务所需能力 |

`source` 当前固定为 `runtime_policy_baseline`。

Runtime 不再通过固定的 `output_contract` 约束模型的回答章节；最终回答的组织形式由用户需求、上下文和模型判断决定。执行类任务的工具调用、权限和验证仍受运行时安全门禁约束。

## 4. 主运行链路

### 4.1 请求入口

Runtime 接收用户消息后：

1. 校验项目、会话和工作区。
2. 恢复或创建本地 Runtime 状态。
3. 必要时提炼相关历史上下文。
4. 调用 `build_task_profile(user_message)`。
5. 根据 TaskProfile 构建本轮模型请求。
6. 进入主模型与工具循环。

这里不存在独立分类模型调用。

### 4.2 动态上下文注入

动态提示词继续使用小块、可追踪的 system message：

- `desktop_runtime.dynamic_task_brief`
- `desktop_runtime.hard_contract`
- `desktop_runtime.execution_plan_rules`
- `desktop_runtime.relevant_history`
- 项目业务上下文
- 代码、UI、安全、媒体或部署规则

只有 TaskProfile 声明需要的上下文才进入主模型请求。

### 4.3 工具暴露

工具列表由 Runtime 和项目配置决定，而不是由前置分类模型生成。

Runtime 必须：

- 只暴露当前真实可用工具。
- 校验工具参数 Schema。
- 在执行前检查权限和风险。
- 将真实工具结果反馈给主模型。
- 对写入任务执行验证门禁。

## 5. 安全边界

移除前置模型分类不等于移除安全控制。

安全边界仍由以下层次负责：

1. Runtime 根据用户原始文本识别只读和明确执行语义。
2. 工具定义限制模型可调用的能力。
3. 权限系统控制写文件、命令、MCP 和外部操作。
4. 高风险操作继续要求用户确认。
5. 验证门禁阻止未验证写入直接宣告完成。

主模型不能通过修改 TaskProfile 文本扩大自己的权限。

## 6. checkpoint 恢复

checkpoint 恢复时：

1. 恢复已有消息、工具结果和当前执行节点。
2. 根据当前用户消息确定性重建 TaskProfile。
3. 直接继续主模型循环。

恢复过程不再发起额外任务分类请求，因此不会因分类 JSON、流式快照或 Schema 解析中断。

## 7. 测试要求

必须覆盖：

- 四种基础意图的确定性分类。
- Runtime 独立生成风险、能力和输出契约。
- 简单回答只注入必要上下文。
- 执行任务注入代码和计划约束。
- 普通流式增量与累计流式快照均能正确合并。
- checkpoint 恢复直接进入主模型链路。
- 工具权限与验证门禁保持有效。

禁止重新引入：

- 每轮对话前的独立通用分类模型请求。
- 主循环启动前必须解析的模型分类 JSON。
- 分类失败后的静默降级或重复分类重试。
- 由模型决定权限、风险和真实工具能力。

## 8. 验收标准

- 主模型请求前不再调用通用任务分类模型。
- Runtime 中不存在 `TaskRouterOutput` 类型和分类器函数。
- TaskProfile 的 `source` 为 `runtime_policy_baseline`。
- 回答、设计、诊断和执行任务仍能获得对应动态上下文。
- checkpoint 恢复不会重复执行前置分类步骤。
- 权限、风险、工具 Schema 和验证门禁行为保持不变。
- Rust 测试与本地聊天契约检查通过。
