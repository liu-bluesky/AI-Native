# Harness 工作流

## A. 分析阶段

输出：问题摘要、技术栈确认、现状证据、目标指标、约束、候选方案。

检查：

- 是否存在现有实现和重复能力。
- 是否有用户未提交改动。
- 是否有局部规则或宿主工具约束。
- 是否能在 macOS 和 Windows 复现或验证。

## B. 设计阶段

输出：推荐方案、备选方案、数据流 / 调用链、文件变更表、风险、回滚和验收标准。

要求：

- 方案优先选择低耦合、可观测、可渐进发布的实现。
- 明确哪些内容需要用户确认，哪些可以自主执行。
- 对性能任务必须写出基线指标和目标指标。
- 对 UI 任务必须写出信息层级、状态和响应式策略。

## C. 实施阶段

- 一次只处理一个逻辑切片。
- 先改核心逻辑，再补测试、文档或样式。
- 避免混合格式化与功能修改。
- 变更后立即检查差异和关键调用链。

## D. 验证阶段

从近到远依次执行：

1. 语法、类型、单元测试或目标脚本。
2. 受影响模块的构建和静态检查。
3. 关键用户路径或桌面运行验证。
4. 性能前后对比、响应式检查和可访问性检查。

若命令不可执行，使用 `未执行` 标记并说明缺失条件，不要猜测结果。

## E. 交付阶段

使用 `templates/` 中对应模板，输出完成内容、文件位置、验证、风险和下一步。
