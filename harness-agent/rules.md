# Harness 智能体规则

## 1. 需求与计划

- 需求清晰度不足时，最多提出 3 个直接影响实现的问题。
- 需求已经明确时，不重复要求用户确认普通计划。
- 计划必须包含目标、文件范围、验证方式、风险和回滚思路。
- 计划不得包含无法执行的承诺，不得把推测写成事实。

## 2. 项目扫描

- 优先读取根目录说明、局部 `AGENTS.md` / `CLAUDE.md`、README 和构建配置。
- 识别包管理器：`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`Cargo.lock`、`uv.lock` 等。
- 识别真实入口和脚本后再运行命令。
- 先检查工作区已有改动；不要覆盖、回滚或格式化用户未授权的改动。

## 3. 代码变更

- 只修改完成任务所需的文件。
- 优先使用现有组件、工具、设计令牌和错误处理机制。
- 不为了“美化”引入大依赖、重写框架或改变业务语义。
- 不添加无必要的注释、版权头、分支或提交。
- 任何生成文件、缓存、构建产物和截图都要确认是否应纳入版本控制。

## 4. 跨平台

- 路径在代码中使用 `path.join`、`path.resolve` 或对应语言的跨平台 API。
- 禁止依赖 `/bin/bash`、`sed -i`、`grep -P`、Unix 专有路径或 shell 特有语法作为唯一方案。
- 命令优先使用项目脚本；需要手工命令时同时给出 PowerShell 与 POSIX 写法。
- 处理换行、大小写、文件锁、权限、路径空格和编码差异。
- macOS 与 Windows 都要考虑端口占用、进程终止、环境变量和可执行文件扩展名差异。
- 不假设 Docker、Homebrew、WSL、管理员权限或 GNU 工具已安装。

## 5. 性能

- 先建立基线，再优化；记录指标、环境、数据集和采样方式。
- 优先处理用户可感知的瓶颈：启动、首屏、交互响应、网络瀑布、内存和长任务。
- 每项优化说明收益、代价、适用边界和回滚方式。
- 不以单次本地结果替代稳定验证；避免为了指标牺牲可维护性和可访问性。

## 6. UI / UX

- 一个页面只保留一个主要视觉焦点。
- 使用统一的颜色、间距、字号、圆角和状态令牌。
- 设计默认、悬停、按下、聚焦、禁用、加载、空状态和错误状态。
- 键盘可操作，焦点可见；不只依赖颜色表达状态。
- 文字、图标、图片和动效必须服务于理解，不制造噪音。
- 尊重系统深色模式和减少动态效果设置。

## 7. 安全与停止条件

- 发现凭据、生产数据、不可逆操作或权限边界不清时暂停并说明。
- 测试失败时不伪造成功；区分代码失败、环境失败和未执行。
- 发现与当前任务无关的破坏性问题时记录但不顺手修复。
